## Сведения о документе

Это спецификация требований к программному обеспечению (Software Requirements Specification, SRS) для IDE разработки прошивок STM32. Структура следует примеру содержания SRS из ISO/IEC/IEEE 29148:2018; исходные данные — [анализ требований (этап 1\)](https://claude.ai/artifact/X7jkxE14vYzfzhdLdz8Gjn) и решения команды от 26 октября 2026\.

| :---- | :---- | :---- |

| 0.2 | 26.10.2026 | Раздел 3 расписан подробно: у каждого требования — пояснение, ожидаемое поведение и критерии приёмки; удалена ссылка на анализ требований из раздела 2 |

**Соглашения, принятые в документе**

- Каждое требование — одно утверждение со словом «должна» (англ. shall), проверяемое и с уникальным идентификатором. Идентификатор не меняется и не переиспользуется.  
- Префиксы: N — потребность пользователя, IF — внешний интерфейс, F — функция, U — удобство использования, P — производительность, D — данные, C — ограничение проектирования, Q — атрибут качества.  
- **Приоритет:** Must — обязательно для MVP; Should — важно, можно в следующей версии 1.x; Could — при наличии времени; Won't — не в текущей версии.  
- **Метод верификации** (см. раздел 4): И — инспекция, А — анализ, Д — демонстрация, Т — тест.  
- **Источник** — потребность (N-xx) или решение команды (Р-xx, раздел 1.6), из которого вытекает требование.

## 1\. Введение

### 1.1 Назначение

SRS задаёт полный набор требований к первой версии IDE (MVP) и к её развитию в версиях 1.x. Документ — основа для этапа 2 (архитектура), этапа 3 (разработка) и приёмки: каждое требование проверяется методом из раздела 4\. Читатели — команда из двух разработчиков и будущие участники открытого проекта.

### 1.2 Область применения

Продукт — настольная IDE для разработки прошивок на C под микроконтроллеры STM32 в Windows 10/11 (рабочее название не выбрано, см. 5.3).

- **Входит:** создание и открытие CMake-проектов STM32, редактирование кода C/C++, сборка внешним тулчейном GCC, прошивка и отладка через ST-Link, монитор последовательного порта.  
- **Не входит:** собственный компилятор, отладчик и драйверы; эмуляция МК; генерация кода периферии; веб\-версия; сертифицируемые отрасли (ISO 26262, MISRA).  
- **Цель и выгода:** путь от установки до мигающего светодиода с пошаговой отладкой — не больше 15 минут; полный контроль команды над инструментом; открытый исходный код.

### 1.3 Перспектива продукта

IDE — самостоятельное приложение, а не расширение другой платформы. Оно запускает внешние инструменты отдельными процессами и связывает их с платой.

```
flowchart TB
  subgraph PC["ПК с Windows 10/11 — процессы, которые запускает IDE"]
    ED["Редактор IDE<br/>подсказки от clangd по LSP"] --> GCC["Сборка: GCC<br/>CMake и Ninja вызывают GCC"] --> LD["Компоновщик<br/>код по адресам памяти → .elf"]
    LD -- "файл .elf" --> OCD["OpenOCD<br/>GDB-сервер и прошивка"]
    GDB["Отладчик GDB<br/>управление через GDB/MI"] <--> OCD
    MON["Монитор порта<br/>вывод printf с платы"]
  end
  subgraph BOARD["Плата STM32 (Nucleo или собственная)"]
    STL["Программатор ST-Link<br/>USB ↔ отладочный порт SWD"] <-- "SWD" --> MCU["Микроконтроллер STM32<br/>ядро Cortex-M, Flash, RAM"]
    MCU --> UART["USB-UART<br/>виртуальный COM-порт"]
  end
  OCD <-- "USB (IF-HW-01)" --> STL
  UART -- "USB (IF-HW-03)" --> MON
```

*Контекстная схема.* Сборка идёт от редактора к файлу .elf; отладка и прошивка — через GDB, OpenOCD и ST-Link к микроконтроллеру; вывод printf приходит в монитор порта через USB-UART. Каждая связь соответствует интерфейсу из 3.1.

| Аспект | Описание |
| :---- | :---- |
| Системные интерфейсы | Внешние инструменты GCC, CMake, Ninja, OpenOCD, GDB, clangd (3.1.3) |
| Пользовательский интерфейс | Одно главное окно: редактор, панели проекта, сборки, отладки и монитора порта (3.1.1) |
| Аппаратные интерфейсы | Программатор ST-Link по USB, целевой МК STM32 по SWD, виртуальный COM-порт (3.1.2) |
| Программные интерфейсы | Протоколы GDB/MI и LSP, формат CMSIS-SVD, Windows API через слой абстракции ОС (3.1.3) |
| Коммуникационные интерфейсы | HTTPS для загрузки инструментов; локальный TCP между GDB и OpenOCD (3.1.4) |
| Ограничения памяти | Не более 1 ГБ ОЗУ при открытом проекте и активной отладке (P-05) |
| Режимы работы | Редактирование, сборка, прошивка, отладка; после установки инструментов работа без интернета |
| Адаптация к месту установки | Пути к инструментам, порт GDB-сервера и каталог плат настраиваются; свои платы добавляются файлами описания |

### 1.4 Функции продукта

1. **Проекты** — создание из шаблона по плате, открытие CMake-проектов, дерево файлов.  
2. **Инструменты и платы** — автозагрузка тулчейна, каталог описаний плат, проверка окружения.  
3. **Редактор кода** — подсветка, автодополнение, диагностика ошибок.  
4. **Сборка** — запуск, разбор ошибок, отчёт о памяти.  
5. **Прошивка** — запись, стирание, сброс МК.  
6. **Отладка** — точки останова, шаги, переменные, регистры периферии.  
7. **Монитор порта** — приём и отправка данных, лог, плоттер.  
8. **Интерфейс** — строка состояния, темы, горячие клавиши, языки.

### 1.7 Допущения и зависимости

Изменение любого пункта требует пересмотра требований.

- Пользователь знает основы языка C.  
- У команды есть плата STM32 (Nucleo или своя) с ST-Link для тестов на железе.  
- Arm GNU Toolchain, CMake, Ninja, OpenOCD, GDB и clangd доступны для загрузки, бесплатны и работают в Windows 10/11.  
- Драйвер ST-Link пользователь устанавливает с правами администратора.  
- SVD-файлы для поддерживаемых чипов доступны и допускают распространение вместе с IDE (проверить лицензию, см. 5.3).

## 3\. Требования

Раздел содержит 82 требования: 63 Must, 14 Should, 5 Could. Каждое оформлено карточкой из четырёх частей:

- **Требование** — нормативный текст «IDE должна…». Именно он проверяется при приёмке.  
- **Пояснение** — зачем требование нужно и что оно значит простыми словами.  
- **Как должно работать** — ожидаемое поведение по шагам, особые случаи и ошибки.  
- **Критерии приёмки** — конкретные проверки; требование выполнено, когда пройдены все.

Строка атрибутов под заголовком: приоритет, источник (N-xx или Р-xx) и метод проверки (И, А, Д, Т — раздел 4). Подсказки по реализации в пояснениях — справочные: окончательные технические решения принимаются на этапе 2\.

### 3.1 Внешние интерфейсы

#### 3.1.1 Пользовательский интерфейс

Пользовательский интерфейс — всё, что разработчик видит на экране. Компоновка намеренно похожа на привычные IDE (Visual Studio, CLion, VS Code), чтобы пользователю не пришлось переучиваться.

##### IF-UI-01. Главное окно

Приоритет: Must · Источник: N-01…N-05 · Проверка: Д

**Требование.** IDE должна иметь одно главное окно с областями: дерево проекта, редактор с вкладками, нижняя панель (вывод сборки, список проблем, монитор порта, консоль отладки), панели отладки и строка состояния.

**Пояснение.** Весь цикл «написал → собрал → прошил → отладил» проходит в одном окне, без переключения между программами. Это основа, на которую опираются почти все функции раздела 3.2.

**Как должно работать:**

1. Слева — дерево файлов проекта (F-03).  
2. В центре — редактор: одна вкладка \= один файл; несохранённый файл помечается на вкладке.  
3. Внизу — панель с вкладками: «Вывод» (журнал инструментов, U-03), «Проблемы» (F-13), «Монитор порта» (F-25), «Консоль отладки».  
4. Справа — панели отладки (переменные, наблюдение, стек, точки останова, регистры периферии); они появляются при запуске отладки (F-21, F-22).  
5. В самом низу — строка состояния (F-28).  
6. Панели скрываются и меняют размер; расположение сохраняется между запусками (U-05).

**Критерии приёмки:**

- [ ] Все перечисленные области есть в окне и открываются из меню «Вид».  
- [ ] Панели скрываются, показываются и меняют размер мышью.  
- [ ] Окно корректно отображается при разрешении от 1366×768 и масштабе Windows от 100 до 200 %.

##### IF-UI-02. Меню, панель инструментов и горячие клавиши

Приоритет: Must · Источник: N-02 · Проверка: И

**Требование.** Каждая команда IDE должна быть доступна из главного меню; сборка, прошивка, запуск и остановка отладки, шаги — также горячими клавишами и кнопками панели инструментов.

**Пояснение.** Меню — «карта» всех возможностей: там новичок находит любую команду. Частые действия (сборка, шаг отладки) выполняются десятки раз в час, поэтому должны быть на расстоянии одного нажатия.

**Как должно работать:**

1. Главное меню: Файл, Правка, Вид, Проект, Сборка, Отладка, Инструменты, Справка.  
2. Панель инструментов: «Собрать», «Прошить», «Начать/остановить отладку», кнопки шагов, выбор конфигурации (F-15) и платы.  
3. Раскладка клавиш по умолчанию следует привычным соглашениям Visual Studio, например: F5 — начать/продолжить отладку, Shift+F5 — остановить, F9 — точка останова, F10 — шаг с обходом, F11 — шаг с заходом, Shift+F11 — выход из функции. Точная раскладка утверждается на этапе 2\.  
4. Рядом с пунктом меню показывается его сочетание клавиш, а у кнопки — всплывающая подсказка с названием и сочетанием.  
5. Недоступная в текущем состоянии команда (например, «Шаг» без запущенной отладки) отображается неактивной.

**Критерии приёмки:**

- [ ] Для каждой команды из раздела 3.2 есть пункт меню.  
- [ ] Сборка, прошивка, запуск/остановка отладки и шаги доступны с клавиатуры и с панели инструментов.  
- [ ] Сочетания клавиш не повторяются.

##### IF-UI-03. Языки интерфейса

Приоритет: Could · Источник: Р-06 · Проверка: Д

**Требование.** IDE должна поддерживать русский и английский языки интерфейса с переключением в настройках.

**Пояснение.** Команда работает по-русски, но открытый проект читают по всему миру. Сам перевод можно отложить (Could), но строки интерфейса нужно с первого дня держать в файлах перевода, а не в коде: иначе потом придётся перебирать весь проект.

**Как должно работать:**

1. Язык выбирается в настройках; допустимо применение после перезапуска.  
2. По умолчанию — язык Windows, если он поддерживается, иначе английский.  
3. Вывод внешних инструментов (GCC, OpenOCD) не переводится; переводятся только сообщения самой IDE и пояснения к ошибкам (U-02).

**Критерии приёмки:**

- [ ] Переключение языка меняет все надписи меню, диалогов и сообщений IDE.  
- [ ] В исходном коде нет строк интерфейса вне файлов перевода (инспекция).

##### IF-UI-04. Темы оформления

**Пояснение.** С кодом работают часами, и многие разработчики предпочитают тёмную тему. Цвета лучше сразу задавать через именованные переменные темы, а не вписывать в каждый виджет.

**Как должно работать:**

1. В настройках выбирается светлая, тёмная или «как в Windows».  
2. Тема применяется сразу, без перезапуска, ко всем панелям, редактору и диалогам.  
3. Для каждой темы есть своя схема подсветки синтаксиса.

**Критерии приёмки:**

- [ ] Тема переключается без перезапуска, и все области окна меняют цвета.  
- [ ] Контраст текста и фона в обеих темах не ниже 4,5:1 (уровень AA стандарта WCAG).

#### 3.1.2 Аппаратные интерфейсы

Аппаратные интерфейсы описывают, с каким железом работает IDE. На платах Nucleo программатор ST-Link уже встроен: один USB-кабель даёт и прошивку с отладкой, и последовательный порт. На собственных платах обычно используют отдельный ST-Link и отдельный адаптер USB-UART. Сама IDE с USB-устройствами программатора напрямую не работает — это делает OpenOCD (IF-SW-03); задача IDE — найти устройство и передать правильную конфигурацию.

##### IF-HW-01. Программатор ST-Link

Приоритет: Must · Источник: N-03 · Проверка: Т

**Требование.** IDE должна работать с программаторами ST-Link V2, V2-1 и V3, включая встроенные в платы Nucleo, подключёнными по USB.

**Пояснение.** ST-Link — устройство-посредник между ПК и микроконтроллером. Версии отличаются USB-идентификаторами и скоростью; на разных платах Nucleo стоят разные версии, поэтому поддержать нужно все три.

**Как должно работать:**

1. IDE находит подключённые ST-Link по USB-идентификаторам (VID/PID) из таблицы, которую ведёт сама IDE.  
2. Если подключено несколько программаторов, IDE показывает список с серийными номерами; выбор запоминается для проекта.  
3. Серийный номер выбранного программатора передаётся в OpenOCD, чтобы тот работал именно с ним.  
4. Подключение и отключение USB распознаются на лету и сразу отражаются в строке состояния (F-28).  
5. Если OpenOCD сообщает об устаревшей прошивке ST-Link, IDE показывает совет обновить её утилитой ST.

**Критерии приёмки:**

- [ ] Прошивка и отладка работают с каждым из трёх типов: V2, V2-1, V3.  
- [ ] При двух подключённых программаторах прошивается именно выбранная плата.  
- [ ] Переподключение USB-кабеля распознаётся без перезапуска IDE.

##### IF-HW-02. Отладочный интерфейс SWD

Приоритет: Must · Источник: Р-03 · Проверка: Т

**Требование.** IDE должна прошивать и отлаживать МК STM32 с ядром Cortex-M через интерфейс SWD.

**Пояснение.** SWD (Serial Wire Debug) — двухпроводный отладочный интерфейс ядер Cortex-M (сигналы SWDIO и SWCLK). Через него программатор пишет Flash, останавливает ядро, читает память и регистры. На своих платах эти контакты нужно вывести на разъём (вместе с GND, питанием и желательно NRST).

**Как должно работать:**

1. Модель чипа и конфигурация OpenOCD для него (например, файл target/stm32f4x.cfg) берутся из описания платы (D-03).  
2. Скорость SWD по умолчанию задаётся в описании платы; при ошибках связи IDE предлагает снизить скорость.  
3. Режим «подключение под сбросом» (connect under reset) включается настройкой платы. Он нужен, когда прошивка усыпляет ядро или перенастраивает выводы SWD, и без сброса к чипу не подключиться.  
4. Если МК не отвечает (нет питания, не подключён SWD), IDE показывает сообщение с возможными причинами (U-02).

**Критерии приёмки:**

- [ ] Прошивка и отладка работают на Nucleo-F401RE и Nucleo-F103RB.  
- [ ] Прошивка работает на собственной плате с внешним ST-Link при наличии файла описания платы.  
- [ ] При отключённом питании МК выводится понятное сообщение, а IDE не зависает.  
- [ ] Режим «подключение под сбросом» позволяет перепрошить плату, чья прошивка отключает SWD.

##### IF-HW-03. Последовательные порты (COM)

Приоритет: Must · Источник: N-05 · Проверка: Т

**Требование.** IDE должна работать с последовательными портами Windows (COM): виртуальным портом ST-Link и адаптерами USB-UART.

**Пояснение.** Самый простой способ узнать, что делает программа на плате, — печатать текст в UART. ST-Link на Nucleo содержит мост USB-UART (виртуальный COM-порт), соединённый с одним из UART МК; в Windows он виден как COMn.

**Как должно работать:**

1. IDE показывает порты с понятными именами из Windows (например, «COM5 — STLink Virtual COM Port»), а не только номера.  
2. Порт выбранного ST-Link предлагается по умолчанию.  
3. Параметры по умолчанию — 115200 бит/с, 8 бит данных, без чётности, 1 стоп-бит (8N1); все параметры настраиваются.  
4. Если порт занят другой программой, IDE так и сообщает.

**Критерии приёмки:**

- [ ] Виртуальный порт Nucleo и адаптеры на распространённых чипах (CH340, CP2102, FT232) открываются и принимают данные.  
- [ ] Попытка открыть занятый порт даёт понятное сообщение, а не зависание.

#### 3.1.3 Программные интерфейсы

Каждый внешний инструмент — отдельная программа. IDE запускает её с нужными аргументами, читает её вывод и превращает его в события интерфейса. Инструменты бывают двух видов:

- **Разовые** (GCC, CMake, Ninja, OpenOCD в режиме прошивки) — запустились, сделали работу, завершились с кодом возврата (0 — успех).  
- **Долгоживущие** (clangd, GDB, OpenOCD в режиме сервера) — работают постоянно и обмениваются с IDE сообщениями по протоколу. Их нужно запускать, следить за ними, перезапускать при падении и корректно останавливать.

Команды в карточках ниже — примеры для понимания; точные аргументы фиксируются на этапе 2\.

##### IF-SW-01. Компилятор GCC

Приоритет: Must · Источник: Р-02, N-02 · Проверка: Т

**Требование.** IDE должна вызывать arm-none-eabi-gcc из Arm GNU Toolchain как внешний процесс и разбирать его сообщения вида «файл:строка:столбец: тип: текст».

**Пояснение.** arm-none-eabi-gcc — кросс-компилятор: работает на ПК, а код создаёт для ARM. Обычно его запускает Ninja по правилам CMake (IF-SW-02), но именно IDE должна понимать его сообщения, чтобы показать ошибки в списке проблем (F-13).

**Как должно работать:**

1. Путь к компилятору передаётся через toolchain-файл CMake, который IDE кладёт в проект при его создании (F-01).  
2. Сообщение `src/main.c:42:5: error: 'x' undeclared` разбирается на файл, строку, столбец, тип (error, warning, note) и текст.  
3. Поясняющие строки (note, «In function…») привязываются к основной ошибке.  
4. Ошибки компоновщика (например, `undefined reference to 'foo'` или переполнение Flash) тоже попадают в список, даже без номера строки.  
5. Относительные пути приводятся к абсолютным, чтобы щелчок по ошибке открывал нужный файл.  
6. Цветной вывод GCC отключается (`-fdiagnostics-color=never`), чтобы в тексте не было служебных символов.

**Критерии приёмки:**

- [ ] Набор из не менее 20 реальных примеров вывода GCC и компоновщика разбирается модульными тестами без ошибок.  
- [ ] Ошибки компоновщика попадают в список проблем.  
- [ ] Пути с пробелами и кириллицей обрабатываются корректно.

##### IF-SW-02. Система сборки CMake и Ninja

Приоритет: Must · Источник: N-08 · Проверка: Т

**Требование.** IDE должна конфигурировать и собирать проект через CMake с генератором Ninja.

**Пояснение.** CMake описывает проект (какие файлы, флаги, библиотеки) и генерирует правила сборки; Ninja быстро их выполняет и пересобирает только изменённое. Благодаря CMake проект собирается и без IDE (C-07).

**Как должно работать:**

1. Конфигурирование, например: `cmake -S . -B build/Debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON`.  
2. Сборка: `cmake --build build/Debug`.  
3. Если CMakeLists.txt изменён, конфигурирование повторяется автоматически.  
4. Ошибки CMake (например, опечатка в CMakeLists.txt) показываются в списке проблем с файлом и строкой.  
5. Каждая конфигурация (Debug, Release) собирается в свой каталог, отдельный от исходников.  
6. CMake создаёт compile\_commands.json — список команд компиляции, нужный clangd (IF-SW-05).

**Критерии приёмки:**

- [ ] Шаблонный проект конфигурируется и собирается в обеих конфигурациях.  
- [ ] После изменения одного .c-файла перекомпилируется только он (видно в журнале).  
- [ ] После правки CMakeLists.txt конфигурирование повторяется само.  
- [ ] В каталоге сборки появляется compile\_commands.json.

##### IF-SW-03. OpenOCD

Приоритет: Must · Источник: N-03 · Проверка: Т

**Требование.** IDE должна запускать OpenOCD как GDB-сервер и как утилиту прошивки, передавая конфигурацию программатора и чипа из описания платы.

**Пояснение.** OpenOCD умеет работать с ST-Link и с чипом. Он используется в двух ролях: разовая прошивка (запустился, записал файл, завершился) и GDB-сервер (работает в фоне всё время отладки и выполняет команды GDB).

**Как должно работать:**

1. Конфигурация собирается из описания платы: файл программатора (`interface/stlink.cfg`), файл чипа (`target/stm32f4x.cfg`), скорость, серийный номер ST-Link.  
2. Прошивка, например: `openocd -f interface/stlink.cfg -f target/stm32f4x.cfg -c "program build/Debug/app.elf verify reset exit"`.  
3. Отладка: OpenOCD запускается с портом для GDB (IF-COM-02); IDE ждёт в его выводе строку готовности (с таймаутом) и только потом подключает GDB.  
4. Весь вывод OpenOCD идёт в журнал (U-03); известные ошибки (нет программатора, нет связи с чипом) распознаются и переводятся в понятные сообщения (U-02).  
5. По окончании отладки IDE останавливает OpenOCD; оставшиеся от прошлых сеансов процессы находятся и закрываются.

**Критерии приёмки:**

- [ ] Прошивка шаблона завершается успешно, с проверкой записи.  
- [ ] После завершения отладки в системе не остаётся процессов openocd.exe.  
- [ ] Ошибки «программатор не найден» и «нет связи с чипом» распознаются и показываются понятным текстом.

##### IF-SW-04. Отладчик GDB через GDB/MI

Приоритет: Must · Источник: N-04 · Проверка: Т

**Требование.** IDE должна управлять отладчиком arm-none-eabi-gdb через машинный интерфейс GDB/MI.

**Пояснение.** GDB умеет всё, что нужно для отладки, но его обычный вывод рассчитан на человека. Режим GDB/MI даёт структурированные ответы, которые программа разбирает надёжно. Все панели отладки IDE (F-19…F-24) — это оболочка над командами MI.

**Как должно работать:**

1. Запуск, например: `arm-none-eabi-gdb --interpreter=mi2 build/Debug/app.elf`, затем подключение к OpenOCD: `-target-select extended-remote localhost:3333`.  
2. Команды IDE превращаются в команды MI: точка останова — `-break-insert main.c:42`, шаг с обходом — `-exec-next`, шаг с заходом — `-exec-step`, продолжить — `-exec-continue`, переменные — `-stack-list-variables`, стек — `-stack-list-frames`, память — `-data-read-memory-bytes`.  
3. Асинхронные события GDB (например, `*stopped` с причиной остановки) обновляют панели и подсветку текущей строки.  
4. Каждая команда помечается номером, и ответ сопоставляется с ней; если ответа нет в течение таймаута (например, 10 с), пользователь получает сообщение.  
5. В консоли отладки опытный пользователь может ввести команду GDB напрямую.

**Критерии приёмки:**

- [ ] Разборщик MI покрыт модульными тестами на записанных реальных ответах GDB.  
- [ ] Все команды F-20 работают на плате.  
- [ ] Если GDB не отвечает, IDE сообщает об этом и не зависает.

##### IF-SW-05. Сервер языка clangd по протоколу LSP

Приоритет: Must · Источник: N-02 · Проверка: Т

**Требование.** IDE должна получать автодополнение, переходы и диагностику от clangd по протоколу LSP, используя compile\_commands.json, созданный CMake.

**Пояснение.** Свой анализатор языка C — огромная работа. clangd (из проекта LLVM) уже понимает код и общается с редактором по протоколу LSP — сообщениями JSON-RPC через стандартные ввод и вывод. IDE реализует клиентскую сторону этого протокола.

**Как должно работать:**

1. clangd запускается при открытии проекта и получает путь к каталогу с compile\_commands.json.  
2. Чтобы clangd находил системные заголовки кросс-компилятора (stdint.h и др.), ему разрешается спрашивать пути у arm-none-eabi-gcc (параметр `--query-driver`).  
3. Используются возможности LSP: открытие и изменение документа, автодополнение, переход к определению, подсказка сигнатуры, диагностика, форматирование (для F-11).  
4. Пока идёт индексация, в строке состояния виден индикатор; при падении clangd перезапускается (Q-01).

**Критерии приёмки:**

- [ ] В шаблонном проекте автодополнение предлагает функции и поля структур периферии (например, GPIOA-\>ODR).  
- [ ] Нет ложных ошибок вида «не найден stdint.h».  
- [ ] Переход к определению работает, в том числе в заголовочные файлы производителя.

##### IF-SW-06. Файлы описания периферии CMSIS-SVD

Приоритет: Should · Источник: N-06 · Проверка: Т

**Требование.** IDE должна читать описания периферии в формате CMSIS-SVD.

**Пояснение.** SVD — XML-файл производителя с описанием всех регистров чипа: адрес, имя, битовые поля, описание. Без него регистр — просто адрес в памяти; с ним — «GPIOA → ODR» с полями ODR0…ODR15, которые сразу понятны.

**Как должно работать:**

1. Путь к SVD-файлу берётся из описания платы (D-03).  
2. Файл разбирается в дерево «периферия → регистры → поля»; учитывается наследование описаний (`derivedFrom`) и значения по умолчанию (размер регистра, права доступа).  
3. Результат используется панелью регистров (F-22).  
4. Разобранный файл кэшируется: SVD для сложных чипов занимает несколько мегабайт.

**Критерии приёмки:**

- [ ] SVD-файлы для STM32F401 и STM32F103 разбираются без ошибок.  
- [ ] Число периферийных блоков и регистров совпадает с исходным файлом.  
- [ ] Наследованные блоки (например, GPIOB от GPIOA) показываются со своими адресами.

##### IF-SW-07. Слой абстракции ОС

Приоритет: Must · Источник: Р-05 · Проверка: И

**Требование.** IDE должна обращаться к функциям ОС (процессы, файлы, последовательные порты, USB) только через слой абстракции ОС.

**Пояснение.** Сейчас цель — Windows, позже macOS и Linux. Если вызовы Windows API разбросаны по всему коду, перенос превратится в переписывание. Слой абстракции — набор интерфейсов (запустить процесс, перечислить порты, подписаться на подключение USB и т. д.), реализованных отдельно для каждой ОС.

**Как должно работать:**

1. Интерфейсы слоя определяются на этапе 2\.  
2. Остальной код IDE использует только эти интерфейсы.  
3. Реализация для Windows лежит в отдельном модуле.  
4. Если выбранная библиотека интерфейса уже даёт кроссплатформенную функцию (например, запуск процесса), её можно использовать вместо собственной — это тоже соответствует требованию.

**Критерии приёмки:**

- [ ] Заголовки Windows (windows.h и др.) подключаются только в модуле слоя ОС.  
- [ ] Это правило проверяется автоматически в CI.

#### 3.1.4 Коммуникационные интерфейсы

##### IF-COM-01. Использование сети

Приоритет: Must · Источник: Q-05 · Проверка: И

**Требование.** IDE должна использовать сеть только для загрузки инструментов и описаний плат, и только по HTTPS.

**Пояснение.** В IDE лежат исходники прошивок — это ценные данные. Чем меньше IDE ходит в сеть, тем меньше рисков. HTTPS защищает от подмены файлов по дороге.

**Как должно работать:**

1. Адреса загрузки берутся из манифеста инструментов: список «что, какой версии, откуда, какая контрольная сумма» (Q-05).  
2. Перед загрузкой пользователь видит, что и откуда будет скачано и сколько это займёт.  
3. Если сети нет, IDE предлагает указать пути к уже установленным инструментам вручную.  
4. Настройки прокси берутся из Windows.

**Критерии приёмки:**

- [ ] Все сетевые обращения собраны в одном модуле загрузки и используют только адреса https\:// (инспекция).  
- [ ] При отключённой сети можно указать инструменты вручную.

##### IF-COM-02. Связь GDB и OpenOCD по локальному TCP

Приоритет: Must · Источник: N-04 · Проверка: Т

**Требование.** IDE должна соединять GDB и OpenOCD через TCP-порт на 127.0.0.1; порт настраивается, а если он занят — IDE выбирает свободный.

**Пояснение.** GDB и OpenOCD — две разные программы, которые разговаривают по сетевому соединению, даже на одном компьютере. По умолчанию OpenOCD слушает порт 3333\. Порт открывается только на локальном адресе 127.0.0.1, чтобы никто из сети не мог подключиться к плате.

**Как должно работать:**

1. Порт по умолчанию — 3333, меняется в настройках.  
2. Перед запуском IDE проверяет, свободен ли порт; если занят — берёт свободный и передаёт один и тот же номер и OpenOCD, и GDB.  
3. IDE явно привязывает OpenOCD к 127.0.0.1 и отключает его ненужные порты (telnet, tcl).

**Критерии приёмки:**

- [ ] Если порт 3333 занят, отладка запускается на другом порту без участия пользователя.  
- [ ] С другого компьютера в сети подключиться к этому порту нельзя.  
- [ ] Два окна IDE могут одновременно отлаживать две разные платы.

#### 3.2.1 Проекты

Проект — это папка с исходниками, CMakeLists.txt и файлом проекта IDE (D-01). Минимальный рабочий проект для микроконтроллера — это не только main.c: нужны startup-файл, скрипт компоновщика, заголовки с описанием регистров чипа и настройка кросс-компилятора. Собрать это вручную — главный барьер для новичка, и группа требований ниже его убирает.

##### F-01. Создание проекта из шаблона

Приоритет: Must · Источник: N-01 · Проверка: Т

**Требование.** По команде «Новый проект» IDE должна создать в выбранной папке проект для выбранной платы из шаблона (CMakeLists.txt, скрипт компоновщика, startup-файл, main.c с миганием светодиода), который собирается без изменений.

**Пояснение.** «Мигающий светодиод» — аналог «Hello, world» для микроконтроллеров: он доказывает, что вся цепочка (сборка, прошивка, запуск) работает. Startup-файл содержит таблицу прерываний и код до main(), скрипт компоновщика говорит, где в чипе Flash и RAM. Оба файла зависят от конкретного чипа и берутся из описания платы.

**Как должно работать:**

1. Мастер «Новый проект» спрашивает: имя, папку, плату из каталога (F-06) и шаблон (в MVP — «Мигающий светодиод»).  
2. IDE копирует файлы шаблона и подставляет в них имя проекта. Примерная структура: `CMakeLists.txt`, `cmake/arm-none-eabi.cmake`, `src/main.c`, `startup/`, `linker/`, `include/` (заголовки CMSIS) и файл проекта IDE.  
3. После создания проект открывается и сразу конфигурируется (IF-SW-02).  
4. Если папка не пуста, IDE предупреждает и не перезаписывает файлы без подтверждения.  
5. Имя проекта проверяется: латиница, цифры, «-» и «\_» (ограничение CMake); при ошибке показывается подсказка.

**Критерии приёмки:**

- [ ] Для каждой платы из каталога проект создаётся и собирается без правок.  
- [ ] После прошивки светодиод на Nucleo мигает с частотой около 1 Гц.  
- [ ] Существующие файлы не перезаписываются без подтверждения.

##### F-02. Открытие существующего CMake-проекта

Приоритет: Must · Источник: N-08 · Проверка: Т

**Требование.** IDE должна открывать как проект любую папку, содержащую CMakeLists.txt.

**Пояснение.** Многие проекты уже существуют — созданы в других инструментах или вручную. Чтобы начать работать с ними в IDE, не должна требоваться миграция или перенос файлов.

**Как должно работать:**

1. Команда «Файл → Открыть папку».  
2. Если в папке нет файла проекта IDE, IDE предлагает выбрать плату (она нужна для прошивки и отладки) и создаёт файл проекта, не трогая CMakeLists.txt.  
3. Если в проекте нет toolchain-файла для ARM, IDE предлагает свой и передаёт его параметром командной строки, а не правкой CMakeLists.txt.  
4. Недавние проекты показываются в меню «Файл».

**Критерии приёмки:**

- [ ] Проект с CMakeLists.txt, созданный вне IDE, открывается, собирается и прошивается.  
- [ ] CMakeLists.txt пользователя при этом не изменяется.  
- [ ] Проект появляется в списке недавних.

##### F-03. Работа с файлами в дереве проекта

Приоритет: Must · Источник: N-01 · Проверка: Д

**Требование.** IDE должна позволять создавать, переименовывать и удалять файлы и папки в дереве проекта.

**Пояснение.** Базовая работа с файлами должна идти без перехода в проводник Windows.

**Как должно работать:**

1. Контекстное меню дерева: «Новый файл», «Новая папка», «Переименовать», «Удалить», «Показать в проводнике».  
2. Удаление идёт в корзину Windows и требует подтверждения.  
3. Изменения, сделанные вне IDE (проводник, Git), появляются в дереве автоматически.  
4. Каталоги сборки показываются приглушёнными или скрываются.  
5. Если создан новый .c-файл, а CMakeLists.txt не подключает файлы автоматически, IDE подсказывает, что файл нужно добавить в сборку.

**Критерии приёмки:**

- [ ] Все операции из п. 1 работают.  
- [ ] Удалённый файл восстанавливается из корзины.  
- [ ] Файл, созданный в проводнике, появляется в дереве не позднее чем через 2 с.

##### F-04. Настройки проекта

Приоритет: Should · Источник: N-01 · Проверка: Т

**Требование.** IDE должна позволять менять настройки проекта (плата, уровень оптимизации, макросы) в окне настроек и сохранять их в файл проекта (D-01).

**Пояснение.** Частые настройки не должны требовать знания CMake. Уровень оптимизации напрямую влияет на отладку: с \-O0 код идёт строка в строку, а с \-Os прошивка меньше, но шаги отладчика «прыгают». Макросы (например, `USE_UART_LOG`) включают и выключают части кода.

**Как должно работать:**

1. Окно «Настройки проекта»: плата, уровень оптимизации отдельно для Debug и Release, список макросов.  
2. Значения сохраняются в файл проекта и передаются в CMake параметрами `-D…`; CMakeLists.txt шаблона их читает.  
3. После изменения проект переконфигурируется.  
4. При смене платы на другой чип IDE предупреждает, что startup-файл и скрипт компоновщика автоматически не заменяются.

**Критерии приёмки:**

- [ ] Новый уровень оптимизации виден в командах компиляции в журнале.  
- [ ] Добавленный макрос доступен в коде через \#ifdef.  
- [ ] Настройки сохраняются после перезапуска IDE.

#### 3.2.2 Инструменты и платы

Ручная установка и настройка инструментов — самая частая причина, по которой разработка под микроконтроллеры застревает на первом дне. Эта группа делает окружение «работающим из коробки» и описывает платы данными, а не кодом.

##### F-05. Автоматическая установка инструментов

Приоритет: Must · Источник: N-01, N-03 · Проверка: Д

**Требование.** При первом запуске IDE должна загрузить и установить Arm GNU Toolchain, CMake, Ninja, OpenOCD и clangd в каталог пользователя с индикатором прогресса, без ручной настройки путей.

**Пояснение.** Инструменты ставятся в каталог пользователя (без прав администратора), каждый — в отдельную папку с номером версии. Системная переменная PATH не меняется: IDE всегда запускает инструменты по полному пути, поэтому не конфликтует с другими программами. Отладчик GDB входит в состав Arm GNU Toolchain.

**Как должно работать:**

1. При первом запуске IDE показывает экран «Установка инструментов»: список, версии, размер и источник каждого (IF-COM-01).  
2. Загрузка идёт с индикатором и кнопкой отмены (U-04); каждый файл проверяется по контрольной сумме (Q-05) и распаковывается, например, в `%LOCALAPPDATA%\<IDE>\tools\<инструмент>-<версия>`.  
3. Если инструмент уже есть в системе, пользователь может указать путь к нему вместо загрузки.  
4. При обрыве связи загрузка возобновляется или повторяется; недокачанные файлы никогда не используются.  
5. Обновление инструментов — только по команде пользователя: новая версия может неожиданно сломать интеграцию (риск в 5.2).

**Критерии приёмки:**

- [ ] На чистом Windows 10 и Windows 11 все инструменты устанавливаются без ручных действий и без прав администратора.  
- [ ] Системная переменная PATH после установки не изменилась.  
- [ ] При обрыве сети во время загрузки установка возобновляется или честно сообщает об ошибке.

##### F-06. Каталог плат из файлов описания

Приоритет: Must · Источник: N-09 · Проверка: Т

**Требование.** IDE должна загружать список плат из файлов описания (D-02); новая плата добавляется копированием файла без пересборки IDE.

**Пояснение.** Плата — это набор фактов: какой чип, сколько памяти, какой программатор, какие файлы OpenOCD, где SVD, какой шаблон проекта. Если держать их в коде, каждая новая плата потребует новой версии IDE. Файл описания — это данные, и команда может сама написать такой файл для своего устройства.

**Как должно работать:**

1. Встроенные описания лежат в каталоге IDE, пользовательские — в профиле пользователя (D-02).  
2. При запуске IDE читает все файлы и проверяет обязательные поля (D-03). Ошибка в одном файле не ломает остальные: плата пропускается, а пользователь видит, какой файл и какое поле исправить.  
3. В мастере проекта платы показываются списком с названием и чипом, есть поиск.  
4. Команда «Обновить каталог плат» перечитывает файлы без перезапуска IDE.  
5. Удобно иметь команду «Создать описание на основе существующего» — копия для своей платы с тем же чипом.

**Критерии приёмки:**

- [ ] Плата, добавленная копированием файла, появляется в каталоге без пересборки IDE.  
- [ ] Файл без обязательного поля отклоняется с понятным сообщением, остальные платы работают.  
- [ ] Пользовательское описание с тем же идентификатором заменяет встроенное.

##### F-07. Проверка окружения

Приоритет: Should · Источник: N-03 · Проверка: Т

**Требование.** IDE должна проверять окружение (инструменты, драйвер ST-Link, доступ к портам) и для каждой проблемы показывать причину и способ исправления.

**Пояснение.** Типичные проблемы — не установлен драйвер ST-Link, порт занят другой программой, инструмент повреждён или удалён. Проверка окружения находит их заранее и сразу подсказывает, что делать.

**Как должно работать:**

1. Команда «Инструменты → Проверить окружение»; также запускается автоматически после установки и при неудачной прошивке.  
2. Проверки: каждый инструмент запускается с `--version` и сверяется версия; установлен ли драйвер ST-Link; виден ли программатор; есть ли место на диске и права на запись в каталог проекта.  
3. Результат — список: проверка, статус, причина и действие (например, «Установите драйвер ST-Link» со ссылкой или «Переустановить инструмент»).  
4. Отчёт можно скопировать, чтобы приложить к обращению за помощью.

**Критерии приёмки:**

- [ ] На ПК без драйвера ST-Link проверка показывает эту проблему и способ исправления.  
- [ ] Удалённый или повреждённый инструмент обнаруживается.  
- [ ] При исправном окружении все проверки проходят успешно.

#### 3.2.3 Редактор кода

В редакторе проходит большая часть времени работы. Базовые функции (подсветка, вкладки, поиск) даёт компонент редактора, выбранный на этапе 2, а «умные» функции (автодополнение, переходы, ошибки) — clangd через LSP (IF-SW-05).

##### F-08. Редактирование, вкладки и поиск

Приоритет: Must · Источник: N-02 · Проверка: Д

**Требование.** IDE должна подсвечивать синтаксис C/C++, открывать файлы во вкладках и выполнять поиск и замену в файле и по проекту.

**Пояснение.** Это минимум редактора программиста, без которого IDE неудобна по сравнению с любым текстовым редактором.

**Как должно работать:**

1. Подсветка C/C++: ключевые слова, строки, комментарии, директивы препроцессора; желательно также ассемблер (startup-файлы .s) и CMake.  
2. Номера строк, подсветка парных скобок, автоотступ, отмена и повтор действий.  
3. Вкладки: открыть, закрыть, переключить (Ctrl+Tab), признак несохранённого файла.  
4. Поиск и замена в файле с опциями «учитывать регистр», «целое слово», «регулярное выражение».  
5. Поиск по проекту: результаты списком, щелчок открывает нужное место.  
6. Кодировка новых файлов — UTF-8; окончания строк существующих файлов сохраняются как были.  
7. Если открытый файл изменён вне IDE, IDE предлагает перезагрузить его.

**Критерии приёмки:**

- [ ] Файл из 10 000 строк открывается и прокручивается без заметных задержек (см. P-02).  
- [ ] Поиск по проекту находит все вхождения, в том числе в заголовочных файлах.  
- [ ] Изменение открытого файла вне IDE обнаруживается.

##### F-09. Автодополнение и переходы по коду

Приоритет: Must · Источник: N-02 · Проверка: Т

**Требование.** IDE должна предлагать автодополнение, переход к определению и подсказки параметров функций.

**Пояснение.** С периферией МК работают через сотни имён регистров и функций (например, GPIOA-\>BSRR, RCC-\>AHB1ENR). Без автодополнения их приходится постоянно искать в документации.

**Как должно работать:**

1. Список подсказок появляется при вводе «.» и «-\>», а также по Ctrl+Пробел.  
2. Переход к определению — F12 или Ctrl+щелчок; есть команда «Вернуться к предыдущему месту».  
3. При вводе «(» показывается сигнатура функции с выделенным текущим параметром.  
4. Данные для всех трёх функций даёт clangd (IF-SW-05); скорость — P-03.

**Критерии приёмки:**

- [ ] В шаблонном проекте после ввода `GPIOA->` предлагаются поля регистра.  
- [ ] F12 на имени функции из заголовков производителя открывает файл на её определении.  
- [ ] При вводе «(» после имени функции показывается её сигнатура.

##### F-10. Ошибки во время редактирования

Приоритет: Should · Источник: N-02 · Проверка: Т

**Требование.** IDE должна подчёркивать ошибки и предупреждения во время редактирования, до запуска сборки.

**Пояснение.** Ошибка, замеченная сразу при наборе, исправляется за секунду; та же ошибка после сборки стоит лишнего цикла «собрал — увидел — исправил».

**Как должно работать:**

1. Ошибки подчёркиваются красной волнистой линией, предупреждения — жёлтой; при наведении показывается текст.  
2. Эти же сообщения попадают в список проблем с пометкой источника «редактор», чтобы отличать их от ошибок сборки.  
3. Диагностика обновляется после короткой паузы в наборе, а не на каждый символ.

**Критерии приёмки:**

- [ ] Опечатка в имени переменной подчёркивается не позднее чем через 2 с, без сборки.  
- [ ] После исправления подчёркивание исчезает.

##### F-11. Форматирование кода

Приоритет: Could · Источник: N-02 · Проверка: Т

**Требование.** IDE должна форматировать код по файлу .clang-format проекта.

**Пояснение.** Единый стиль кода у двух разработчиков без споров: правила записаны в файле .clang-format в корне проекта, а не в настройках каждого редактора.

**Как должно работать:**

1. Команды «Форматировать документ» и «Форматировать выделение».  
2. Настройка «Форматировать при сохранении».  
3. Шаблон проекта (F-01) содержит .clang-format по умолчанию.

**Критерии приёмки:**

- [ ] Результат форматирования совпадает с результатом clang-format из командной строки.  
- [ ] При включённой настройке файл форматируется при сохранении.

#### 3.2.4 Сборка

Сборка превращает исходники в файл прошивки. Главный результат — .elf: в нём и машинный код, и отладочная информация (имена переменных, номера строк), нужная GDB. Из него можно получить .bin или .hex для других программаторов. Компоновщик также создаёт .map-файл — карту распределения памяти.

##### F-12. Команды сборки

Приоритет: Must · Источник: N-02 · Проверка: Т

**Требование.** IDE должна выполнять команды «Собрать», «Пересобрать» и «Очистить» для активной конфигурации.

**Пояснение.** «Собрать» пересобирает только изменённое — это быстро. «Пересобрать» очищает и собирает всё заново, когда что-то пошло не так. «Очистить» удаляет результаты сборки.

**Как должно работать:**

1. Команды доступны из меню «Сборка», с панели инструментов и горячими клавишами (IF-UI-02).  
2. Перед сборкой несохранённые файлы сохраняются автоматически (поведение настраивается).  
3. Во время сборки доступна команда «Остановить сборку»; повторный запуск не создаёт второй процесс.  
4. Итог показывается в строке состояния: успех или ошибка, время сборки, число ошибок и предупреждений.  
5. Ненулевой код возврата считается неудачей, даже если IDE не распознала ни одной ошибки.

**Критерии приёмки:**

- [ ] Все три команды работают для Debug и Release.  
- [ ] Несохранённые изменения попадают в сборку.  
- [ ] После «Остановить сборку» в системе не остаётся процессов ninja и gcc.

##### F-13. Вывод сборки и список проблем

Приоритет: Must · Источник: N-02 · Проверка: Т

**Требование.** IDE должна показывать полный вывод сборки, а ошибки и предупреждения — в списке проблем; выбор пункта открывает файл на нужной строке.

**Пояснение.** Полный вывод нужен, чтобы понимать, что происходит (принцип прозрачности), а список проблем — чтобы быстро их исправлять.

**Как должно работать:**

1. Вкладка «Вывод» показывает весь вывод как есть, по мере его появления.  
2. Вкладка «Проблемы» — таблица: тип, текст, файл, строка; сортировка и фильтр по типу.  
3. Двойной щелчок открывает файл и ставит курсор на строку и столбец; в редакторе такие строки помечены значком.  
4. Есть команды «Следующая ошибка» и «Предыдущая ошибка».  
5. При новой сборке список очищается.

**Критерии приёмки:**

- [ ] Каждая ошибка и каждое предупреждение из вывода есть в списке проблем.  
- [ ] Переход по ошибке попадает точно в строку и столбец.  
- [ ] Вывод появляется по ходу сборки, а не целиком в конце.

##### F-14. Отчёт о занятой памяти

Приоритет: Must · Источник: N-07 · Проверка: Т

**Требование.** После успешной сборки IDE должна показывать занятость Flash и RAM: занято и всего в байтах и процент.

**Пояснение.** Памяти в МК мало: например, у STM32F103RB 128 КБ Flash и 20 КБ RAM. Flash занимают код и константы, RAM — переменные, а также стек и куча, если они зарезервированы в скрипте компоновщика. Видеть запас нужно заранее, а не в момент, когда сборка уже упала.

**Как должно работать:**

1. После сборки IDE получает размеры секций (например, утилитой arm-none-eabi-size или из .map-файла), а объёмы памяти — из описания платы.  
2. Результат в виде: «Flash: 12 340 из 131 072 байт (9,4 %)», «RAM: 2 112 из 20 480 байт (10,3 %)».  
3. При занятости выше 90 % — предупреждение.  
4. Если памяти не хватило и компоновка упала, IDE объясняет, какой области не хватило и на сколько байт.  
5. В дальнейшем полезно показывать самые крупные функции и переменные.

**Критерии приёмки:**

- [ ] Цифры совпадают с выводом arm-none-eabi-size для того же .elf.  
- [ ] Процент считается от объёма памяти из описания платы.  
- [ ] Переполнение Flash даёт понятное сообщение.

##### F-15. Конфигурации Debug и Release

Приоритет: Should · Источник: N-07 · Проверка: Т

**Требование.** IDE должна поддерживать конфигурации Debug и Release с переключением в панели инструментов.

**Пояснение.** Debug — без оптимизации и с отладочной информацией: удобно отлаживать. Release — с оптимизацией: прошивка меньше и быстрее, но отлаживать её сложнее. Для готового устройства обычно прошивают Release.

**Как должно работать:**

1. Переключатель конфигурации на панели инструментов.  
2. У каждой конфигурации свой каталог сборки (IF-SW-02), поэтому переключение не требует полной пересборки.  
3. Прошивка и отладка используют активную конфигурацию; при запуске отладки в Release IDE предупреждает, что шаги могут вести себя неожиданно.

**Критерии приёмки:**

- [ ] Флаги компиляции в журнале соответствуют выбранной конфигурации.  
- [ ] Переключение туда и обратно не вызывает полной пересборки.  
- [ ] Размер прошивки шаблона в Release меньше, чем в Debug.

#### 3.2.5 Прошивка

Прошивка — запись собранной программы во Flash-память микроконтроллера через ST-Link. После записи МК сбрасывается и начинает выполнять новую программу. Саму запись выполняет OpenOCD (IF-SW-03), IDE отвечает за то, чтобы это была одна кнопка и понятные сообщения при проблемах.

##### F-16. Прошивка одной командой

Приоритет: Must · Источник: N-03 · Проверка: Т

**Требование.** По команде «Прошить» IDE должна при необходимости собрать проект, записать прошивку в МК, проверить запись и сбросить МК.

**Пояснение.** «Проверить запись» — прочитать Flash обратно и сравнить с файлом, чтобы исключить сбои. «Сбросить МК» — запустить новую программу с начала. Всё это — одно действие для пользователя.

**Как должно работать:**

1. Если исходники изменены после последней сборки, сначала выполняется сборка (F-12); при ошибке сборки прошивка не начинается.  
2. IDE запускает OpenOCD с командой записи, проверки и сброса (IF-SW-03).  
3. Пользователь видит этапы: подключение → стирание → запись → проверка → сброс.  
4. Успех — сообщение с временем прошивки; ошибка — понятный текст (U-02) и полный вывод в журнале.  
5. Если идёт сеанс отладки, IDE предлагает сначала его остановить.  
6. После прошивки монитор порта переподключается (F-26).

**Критерии приёмки:**

- [ ] Шаблонный проект прошивается и запускается на Nucleo.  
- [ ] При изменённом исходнике сначала выполняется сборка; при ошибке сборки плата не перепрошивается.  
- [ ] Прошивка уже собранного шаблона занимает не более 10 с.

##### F-17. Поиск программатора и понятные ошибки

Приоритет: Must · Источник: N-03 · Проверка: Т

**Требование.** IDE должна сама находить подключённый ST-Link; если программатор не найден, за 5 с или быстрее показать сообщение с вероятными причинами.

**Пояснение.** «Не прошивается» — самая частая проблема. Типичные причины: кабель только для зарядки (без линий данных), не установлен драйвер, плата не подключена, ST-Link занят другой программой. Вместо сырой ошибки OpenOCD IDE должна сказать, что проверить.

**Как должно работать:**

1. IDE постоянно следит за подключением ST-Link (IF-HW-01) и показывает его в строке состояния (F-28).  
2. Если при команде «Прошить» программатор не найден, IDE показывает «Программатор ST-Link не найден» и список проверок: плата подключена, кабель с линиями данных, драйвер установлен (кнопка «Проверить окружение», F-07), другие программы закрыты.  
3. Если программатор найден, но связи с МК нет, сообщение другое: проверьте питание и провода SWD, попробуйте «подключение под сбросом» (IF-HW-02).

**Критерии приёмки:**

- [ ] Без подключённой платы сообщение появляется не позднее чем через 5 с.  
- [ ] Сообщения «нет программатора» и «нет связи с МК» различаются.  
- [ ] После подключения платы статус обновляется без перезапуска IDE.

##### F-18. Стирание Flash и сброс МК

Приоритет: Should · Источник: N-03 · Проверка: Т

**Требование.** IDE должна выполнять полное стирание Flash и сброс МК отдельными командами.

**Пояснение.** Полное стирание нужно, когда старую программу надо убрать целиком (например, она мешает подключиться или в памяти остались данные старой версии). Сброс перезапускает программу без перепрошивки — удобно, чтобы увидеть стартовый вывод в мониторе порта.

**Как должно работать:**

1. Команды «Стереть Flash» и «Сбросить МК» в меню.  
2. Перед стиранием запрашивается подтверждение.  
3. Сброс — аппаратный (через вывод NRST), если он подключён, иначе программный через ядро.

**Критерии приёмки:**

- [ ] После стирания и сброса светодиод шаблона больше не мигает — программа удалена.  
- [ ] После «Сбросить МК» программа начинается заново (стартовый вывод виден в мониторе порта).

#### 3.2.6 Отладка

Отладка на железе — главное отличие нашей IDE от простых инструментов. Программа выполняется на реальном микроконтроллере, а ПК через ST-Link может остановить ядро, прочитать память и регистры и выполнять код по шагам. Цепочка такая: панели IDE → команды GDB/MI (IF-SW-04) → GDB → OpenOCD (IF-SW-03) → ST-Link → SWD → ядро Cortex-M.

##### F-19. Запуск сеанса отладки

Приоритет: Must · Источник: N-04 · Проверка: Т

**Требование.** По команде «Начать отладку» IDE должна собрать и прошить проект, запустить GDB-сервер и GDB и остановить выполнение в начале main().

**Пояснение.** Для пользователя это одна кнопка (F5), а под ней — цепочка из нескольких шагов, каждый из которых может завершиться ошибкой. Остановка именно в main(), а не в самом начале, нужна потому, что до main() работает startup-код, который пользователю обычно не интересен.

**Как должно работать:**

1. Сборка активной конфигурации, если она нужна (F-12).  
2. Запуск OpenOCD как GDB-сервера и ожидание его готовности (IF-SW-03).  
3. Запуск GDB с файлом .elf и подключение к OpenOCD (IF-SW-04, IF-COM-02).  
4. Загрузка прошивки в МК, сброс и остановка ядра.  
5. Временная точка останова на main() и запуск: выполнение останавливается на первой строке main().  
6. IDE переходит в режим отладки: появляются панели, подсвечивается текущая строка, становятся активны команды шагов.  
7. Команда «Остановить» закрывает GDB и OpenOCD и возвращает IDE в режим редактирования; МК сбрасывается, и программа работает сама.  
8. При ошибке на любом шаге IDE показывает, на каком именно, и закрывает уже запущенные процессы.

**Критерии приёмки:**

- [ ] Для уже собранного шаблона от команды до остановки в main() проходит не более 10 с.  
- [ ] После «Остановить» в системе нет процессов gdb и openocd.  
- [ ] Ошибка на любом шаге не оставляет IDE в «полуотладочном» состоянии.

##### F-20. Точки останова и шаги

Приоритет: Must · Источник: N-04 · Проверка: Т

**Требование.** IDE должна ставить и снимать точки останова щелчком по полю редактора и выполнять команды «Продолжить», «Пауза», «Шаг с заходом», «Шаг с обходом», «Выход из функции», «Остановить».

**Пояснение.** Точка останова — место, где программа остановится. «Шаг с обходом» выполняет строку целиком, не заходя в вызываемые функции; «шаг с заходом» заходит внутрь; «выход из функции» доводит текущую функцию до конца. Особенность МК: код лежит во Flash, поэтому точки останова реализуются аппаратно, и их число ограничено (обычно 6 у Cortex-M3/M4 и 4 у Cortex-M0/M0+).

**Как должно работать:**

1. Щелчок по полю слева от номера строки или F9 ставит и снимает точку; она отображается красным кружком.  
2. Точки можно ставить до запуска отладки — они применяются при старте и сохраняются между сеансами.  
3. Если на строке нет кода (комментарий, пустая строка), точка переносится на ближайшую строку с кодом.  
4. Если точек больше, чем аппаратных слотов, IDE сообщает об ограничении и помечает лишние неактивными.  
5. «Пауза» останавливает работающую программу в текущем месте; если для этого места нет исходника, IDE сообщает об этом или показывает дизассемблер (F-23).  
6. Панель «Точки останова»: список, включение и выключение, «Удалить все».

**Критерии приёмки:**

- [ ] Каждая из шести команд работает на шаблонном проекте.  
- [ ] Точки, поставленные до запуска отладки, срабатывают.  
- [ ] При превышении лимита точек показывается понятное сообщение.

##### F-21. Переменные, наблюдение и стек вызовов

Приоритет: Must · Источник: N-04 · Проверка: Т

**Требование.** При остановке IDE должна показывать локальные переменные, выражения наблюдения и стек вызовов и подсвечивать текущую строку.

**Пояснение.** Главная ценность отладки — видеть значения в момент остановки и понимать, как программа пришла в эту точку. Стек вызовов — цепочка функций от main() до текущей.

**Как должно работать:**

1. Панель «Переменные»: локальные переменные текущей функции с типами и значениями; структуры и массивы раскрываются деревом, у указателей виден адрес.  
2. Панель «Наблюдение»: пользователь добавляет выражения (`counter`, `buf[3]`, `GPIOA->ODR`), они пересчитываются при каждой остановке.  
3. Значения, изменившиеся с прошлой остановки, выделяются цветом.  
4. Значение переменной можно изменить двойным щелчком — новое значение записывается в память МК.  
5. Панель «Стек вызовов»: выбор строки показывает переменные этой функции и место вызова в коде.  
6. Числа переключаются между десятичным и шестнадцатеричным видом.  
7. Наведение курсора на переменную в редакторе показывает её значение.

**Критерии приёмки:**

- [ ] Локальные переменные, структура и массив отображаются правильно.  
- [ ] Выражение в «Наблюдении» обновляется после каждого шага.  
- [ ] Выбор другого кадра стека показывает его переменные.  
- [ ] Изменённое в панели значение реально записывается в МК (видно по поведению программы).

##### F-22. Регистры периферии

Приоритет: Should · Источник: N-06 · Проверка: Т

**Требование.** IDE должна показывать регистры периферии по именам из SVD-файла платы с расшифровкой битовых полей.

**Пояснение.** Ошибки настройки железа в переменных не видны — только в регистрах. Пример: светодиод не горит, а в регистре тактирования RCC бит включения порта GPIOA равен 0 — значит, порт не включён.

**Как должно работать:**

1. Панель «Периферия» показывает дерево блоков из SVD (IF-SW-06): GPIOA, RCC, USART2 и т. д.  
2. Регистры читаются из МК только для раскрытых блоков и только при остановке: регистров тысячи, и чтение всех замедлило бы шаги.  
3. Для регистра показываются адрес, значение в hex и поля с именами, значениями и описаниями из SVD.  
4. Поля, изменившиеся с прошлой остановки, выделяются.  
5. Регистры, чтение которых меняет состояние железа (например, регистр данных UART; в SVD они помечены атрибутом readAction), автоматически не читаются — только по явной команде.

**Критерии приёмки:**

- [ ] В шаблонном проекте в регистре выходных данных порта виден бит светодиода, меняющийся при шагах.  
- [ ] Регистры с побочным эффектом чтения не читаются автоматически.  
- [ ] Раскрытие блока занимает не более 1 с.

##### F-23. Память, регистры ядра и дизассемблер

Приоритет: Could · Источник: N-06 · Проверка: Т

**Требование.** IDE должна показывать память по адресу в шестнадцатеричном виде, регистры ядра и дизассемблированный код.

**Пояснение.** Это инструменты для сложных случаев: посмотреть буфер в памяти, понять, что делает код без исходника, проверить регистры ядра (PC — адрес текущей команды, SP — указатель стека, LR — адрес возврата).

**Как должно работать:**

1. Панель «Память»: ввод адреса или выражения (например, `&buf`), байты в hex и текстом, обновление при остановке.  
2. Панель «Регистры ядра»: R0–R12, SP, LR, PC, xPSR.  
3. Панель «Дизассемблер»: машинные команды вокруг PC, при наличии исходника — вперемежку со строками C; шаг по одной машинной команде.

**Критерии приёмки:**

- [ ] Содержимое массива в панели памяти совпадает со значением в «Переменных».  
- [ ] Значение PC совпадает с подсвеченной командой в дизассемблере.  
- [ ] Шаг по машинной команде работает.

##### F-24. Разбор HardFault

Приоритет: Could · Источник: N-04 · Проверка: Т

**Требование.** При HardFault IDE должна остановить выполнение и показать регистры неисправностей с расшифровкой вероятной причины.

**Пояснение.** HardFault — аварийная остановка ядра Cortex-M: обращение по неверному адресу, переполнение стека, недопустимая команда. Без подсказки программа просто «зависает» в обработчике, и непонятно, что случилось. Причину хранят системные регистры неисправностей (CFSR, HFSR, BFAR, MMFAR) — они есть у Cortex-M3/M4/M7, но нет у Cortex-M0/M0+.

**Как должно работать:**

1. На время отладки IDE включает перехват HardFault (например, точкой останова на обработчике или средствами OpenOCD).  
2. При срабатывании IDE показывает окно «Произошёл HardFault»: причину простыми словами (например, «обращение к памяти по недопустимому адресу 0x…») и адрес команды, которая его вызвала.  
3. Кнопка «Перейти к коду» открывает строку, где произошла ошибка.  
4. Для ядер без регистров неисправностей показывается упрощённое сообщение с местом ошибки.

**Критерии приёмки:**

- [ ] Тестовая программа с обращением по неверному указателю вызывает окно с правильной причиной.  
- [ ] «Перейти к коду» открывает строку, вызвавшую ошибку.

#### 3.2.7 Монитор порта

Монитор порта — самый простой способ узнать, что делает программа, не останавливая её. Чтобы printf на МК печатал в UART, в прошивке перенаправляется системная функция вывода (обычно `_write`); шаблоны проектов полезно сразу снабдить таким перенаправлением.

##### F-25. Приём и отправка данных

Приоритет: Must · Источник: N-05 · Проверка: Т

**Требование.** IDE должна показывать список последовательных портов, открывать выбранный порт на скорости от 1200 до 921600 бит/с, выводить принятый текст и отправлять введённый.

**Пояснение.** Скорость на ПК и в прошивке должна совпадать, иначе вместо текста будут «кракозябры» — это частая ошибка новичка. Отправка текста позволяет посылать прошивке команды.

**Как должно работать:**

1. Выбор порта из списка (IF-HW-03) и скорости из стандартного ряда или вводом своего значения; кнопка «Подключить / Отключить».  
2. Принятые данные показываются как текст; непечатаемые байты — в виде кодов; есть режим показа в hex.  
3. Строка ввода отправляется по Enter с выбранным окончанием строки (нет, LF, CR, CR+LF).  
4. Буфер окна ограничен (например, 100 000 строк), старые строки удаляются; автопрокрутку можно приостановить; окно можно очистить.  
5. Монитор работает и во время отладки, и без неё.

**Критерии приёмки:**

- [ ] Текст от printf из тестовой прошивки виден на скорости 115200\.  
- [ ] Строка, отправленная из IDE, возвращается от прошивки-«эхо» без искажений.  
- [ ] Длительный поток данных не замедляет интерфейс (см. P-07).

##### F-26. Переподключение, метки времени и лог

Приоритет: Should · Источник: N-05 · Проверка: Т

**Требование.** IDE должна автоматически переподключать монитор после прошивки, добавлять метки времени и сохранять лог в файл.

**Пояснение.** При прошивке или переподключении кабеля виртуальный COM-порт может на мгновение исчезнуть; переподключаться вручную каждый раз неудобно. Метки времени помогают оценить интервалы между событиями, а лог — разобрать проблему позже.

**Как должно работать:**

1. Если порт пропал, монитор пытается открыть его снова в течение нескольких секунд (например, 10 с); если не удалось — сообщает об этом.  
2. Опция «Метки времени»: каждая строка начинается со времени приёма на ПК (чч:мм:сс.мс).  
3. Команда «Сохранить лог» пишет текущее содержимое в файл; режим «Записывать в файл» дописывает всё новое.

**Критерии приёмки:**

- [ ] После прошивки монитор сам продолжает приём данных.  
- [ ] Метки времени имеют точность до миллисекунд.  
- [ ] Сохранённый файл совпадает с содержимым окна.

##### F-27. Плоттер

Приоритет: Could · Источник: N-05 · Проверка: Д

**Требование.** IDE должна строить график чисел, принимаемых из порта.

**Пояснение.** Показания датчиков и АЦП нагляднее смотреть на графике, чем в столбике чисел: сразу видны шум, всплески и тренд.

**Как должно работать:**

1. В режиме «Плоттер» каждая строка вида `12.5` или `12.5,30,7` даёт по одной точке в одном или нескольких рядах; допустимы имена рядов (`temp:12.5 hum:30`).  
2. График прокручивается и показывает последние N точек (например, 1000).  
3. Есть пауза, масштабирование и сохранение данных в CSV.

**Критерии приёмки:**

- [ ] Синусоида, отправляемая с платы, отображается плавной кривой.  
- [ ] Три числа в одной строке отображаются тремя разными линиями.

#### 3.2.8 Состояние системы

##### F-28. Строка состояния

Приоритет: Must · Источник: N-03 · Проверка: Д

**Требование.** IDE должна показывать в строке состояния выбранную плату, найденный программатор и состояние подключения.

**Пояснение.** Одного взгляда должно хватать, чтобы понять, всё ли готово: выбрана ли нужная плата, подключён ли программатор, идёт ли сборка или отладка.

**Как должно работать:**

1. В строке состояния: проект и конфигурация; плата; программатор (подключён / не найден, серийный номер во всплывающей подсказке); текущее действие (готово, сборка, прошивка, отладка — идёт или на паузе); состояние индексации кода.  
2. Щелчок по плате открывает выбор платы, по программатору — список программаторов, по текущему действию — журнал.  
3. Всё обновляется сразу, без действий пользователя.

**Критерии приёмки:**

- [ ] Отключение USB-кабеля отражается в строке состояния не позднее чем через 2 с.  
- [ ] При запуске и остановке отладки состояние меняется.  
- [ ] Щелчки по элементам открывают соответствующие окна.

### 3.3 Требования к удобству использования

Эти требования описывают не отдельные функции, а то, насколько легко пользоваться IDE в целом. Именно здесь закреплена главная цель продукта — 15 минут от установки до отладки на плате.

#### U-01. От установки до отладки за 15 минут

Приоритет: Must · Источник: цель продукта (1.2) · Проверка: Т

**Требование.** Новый пользователь из целевой группы (1.5) должен пройти путь от запуска установщика до мигающего светодиода на Nucleo и остановки на точке останова за 15 минут или быстрее, не открывая документацию.

**Пояснение.** Это интегральная проверка всего продукта: она проходит, только если работают установка, шаблон, сборка, прошивка и отладка, а интерфейс понятен без инструкций. Проверяет человек, не участвовавший в разработке.

**Как проводится проверка:**

1. Чистый ПК с Windows, интернет не медленнее 50 Мбит/с, плата Nucleo и USB-кабель.  
2. Участник получает только установщик IDE и задачу: установить IDE, создать проект для платы, прошить, убедиться, что светодиод мигает, поставить точку останова в цикле и посмотреть значение переменной.  
3. Время измеряется от запуска установщика до остановки на точке останова.  
4. Все места, где участник застрял или засомневался, записываются и становятся задачами на улучшение.

**Критерии приёмки:**

- [ ] Минимум два участника укладываются в 15 минут.  
- [ ] Ни одному участнику не понадобились подсказки или документация.

#### U-02. Понятные сообщения об ошибках

Приоритет: Must · Источник: N-03 · Проверка: Т

**Требование.** Для 10 самых частых ошибок окружения IDE должна показывать пояснение «что случилось и что делать».

**Пояснение.** Исходные сообщения OpenOCD и GDB писались для специалистов (например, строка с кодом ошибки libusb). IDE распознаёт известные случаи и объясняет их простыми словами, не скрывая исходный текст.

**Как должно работать:**

1. Таблица известных ошибок «шаблон текста → объяснение → действия» хранится как данные, её можно дополнять без изменения кода.  
2. Начальный список из 10 ситуаций: программатор не найден; не установлен драйвер; нет связи с МК; COM-порт занят; порт GDB занят; инструмент не найден или повреждён; не хватило Flash или RAM; не найден компилятор; ошибка проверки после записи; МК защищён от чтения.  
3. Сообщение состоит из заголовка, блоков «Что случилось» и «Что сделать» и кнопки «Подробнее» с исходным выводом инструмента.

**Критерии приёмки:**

- [ ] Каждая из 10 ситуаций воспроизведена, и IDE показывает правильное объяснение.  
- [ ] Исходный текст ошибки всегда доступен.

#### U-03. Журнал команд инструментов

Приоритет: Must · Источник: принцип прозрачности · Проверка: Д

**Требование.** IDE должна записывать в журнал вывода каждую командную строку внешнего инструмента и его вывод.

**Пояснение.** Пользователь видит, что именно делает IDE, может повторить команду вручную в терминале и разобраться, если что-то пошло не так. Для команды разработки это главный инструмент диагностики.

**Как должно работать:**

1. Перед выводом каждого запуска в журнал пишется полная командная строка и рабочий каталог.  
2. По завершении записываются код возврата и длительность.  
3. Журнал можно скопировать и сохранить в файл.  
4. Журналы нескольких последних сеансов сохраняются в профиле пользователя для разбора проблем.

**Критерии приёмки:**

- [ ] Команда сборки, скопированная из журнала и выполненная в терминале, даёт тот же результат.  
- [ ] Для каждого запуска виден код возврата.

#### U-04. Прогресс и отмена долгих операций

Приоритет: Must · Источник: N-01…N-04 · Проверка: Т

**Требование.** Операции дольше 1 с (сборка, загрузка, прошивка) IDE должна сопровождать индикатором прогресса и давать их отменить.

**Пояснение.** Если окно замирает на несколько секунд, пользователь думает, что IDE зависла. Долгие операции должны идти в фоне, а интерфейс — оставаться отзывчивым.

**Как должно работать:**

1. Сборка, загрузка инструментов, прошивка, запуск отладки и индексация выполняются вне потока интерфейса.  
2. Индикатор показывает процент, если он известен, иначе — просто что операция идёт.  
3. Кнопка «Отмена» завершает операцию и все её процессы и убирает недоделанные результаты.  
4. Во время операции можно двигать окно, прокручивать и редактировать код.

**Критерии приёмки:**

- [ ] Во время сборки набор текста не замедляется (см. P-02).  
- [ ] Отмена каждой долгой операции работает и не оставляет процессов.

#### U-05. Сохранение состояния окна

Приоритет: Should · Источник: N-02 · Проверка: Д

**Требование.** IDE должна сохранять расположение панелей, открытые файлы и последний проект между запусками.

**Пояснение.** После перезапуска можно сразу продолжить работу с того же места.

**Как должно работать:**

1. Сохраняются размер и положение окна, расположение панелей, открытые вкладки и положение курсора, последний проект (D-04).  
2. При следующем запуске всё восстанавливается.  
3. Если какой-то файл удалён, его вкладка просто не открывается, без сообщений об ошибке.

**Критерии приёмки:**

- [ ] После перезапуска IDE окно, панели и вкладки выглядят так же, как до закрытия.  
- [ ] Удалённый между запусками файл не мешает запуску.

### 3.4 Требования к производительности

Значения измеряются на эталонном ПК: Windows 10/11 x64, 4 ядра, 8 ГБ ОЗУ, SSD. Цифры уточняются после первого прототипа.

Чтобы цифры можно было проверить, у каждого требования есть методика измерения. Измерения повторяются несколько раз: «медиана» — среднее по порядку значение, «95-й перцентиль» — значение, которое не превышают 95 % замеров.

#### P-01. Время запуска

Приоритет: Must · Проверка: Т

**Требование.** IDE должна запускаться до готовности главного окна за 5 с или быстрее.

**Обоснование.** Лёгкость — ключевое отличие от тяжёлых IDE; среду перезапускают несколько раз в день.

**Как измерять.** Время от запуска исполняемого файла до момента, когда окно с открытым шаблонным проектом отвечает на ввод. Пять повторных («тёплых») запусков; запуск сразу после включения ПК фиксируется для сведения.

- [ ] Медиана пяти тёплых запусков — не более 5 с.

#### P-02. Задержка при наборе текста

Приоритет: Must · Проверка: Т

**Требование.** Задержка отображения символа при наборе должна быть не более 50 мс.

**Обоснование.** Задержка выше десятков миллисекунд заметна и раздражает; самое простое действие в IDE должно быть мгновенным.

**Как измерять.** Автотест посылает нажатия клавиш в файл из 10 000 строк и замеряет время до перерисовки (счётчики времени встраиваются в тестовую сборку IDE). Замер повторяется во время идущей сборки.

- [ ] 95-й перцентиль задержки — не более 50 мс, в том числе во время сборки.

#### P-03. Скорость автодополнения

Приоритет: Should · Проверка: Т

**Требование.** Автодополнение должно появляться не позднее 300 мс в проекте до 200 исходных файлов после завершения индексации.

**Обоснование.** Подсказка полезна, только пока слово не допечатано вручную.

**Как измерять.** Тестовый проект из 200 файлов создаётся скриптом. После индексации — 20 вызовов автодополнения в разных местах; время от ввода «-\>» до появления списка.

- [ ] 95-й перцентиль — не более 300 мс.

#### P-04. Скорость повторной сборки

Приоритет: Must · Проверка: Т

**Требование.** Повторная сборка шаблонного проекта после изменения одного файла должна занимать не более 5 с.

**Обоснование.** Цикл «правка → проверка» повторяется сотни раз в день. Саму компиляцию выполняют GCC и Ninja; требование ограничивает прежде всего накладные расходы IDE вокруг них.

**Как измерять.** Шаблон уже собран; изменяется один .c-файл; время от команды «Собрать» до сообщения об успехе. Пять замеров.

- [ ] Медиана — не более 5 с.

#### P-05. Потребление памяти

Приоритет: Must · Проверка: Т

**Требование.** Процесс IDE должен занимать не более 1 ГБ ОЗУ при открытом проекте и активной отладке (без учёта внешних инструментов).

**Обоснование.** IDE должна комфортно работать на ноутбуке с 8 ГБ рядом с браузером и документацией.

**Как измерять.** Открыть шаблон и 5 файлов, запустить отладку с открытыми панелями и 30 минут работать (шаги, сборки, монитор порта). Следить за памятью процесса IDE в системных счётчиках Windows.

- [ ] Максимум за 30 минут — не более 1 ГБ.  
- [ ] Память не растёт непрерывно (нет признаков утечки).

#### P-06. Отклик шага отладки

Приоритет: Should · Проверка: Т

**Требование.** После команды «Шаг с обходом» панели отладки должны обновиться не позднее 1 с.

**Обоснование.** При пошаговой отладке команду нажимают десятки раз подряд. Часть времени уходит на обмен через ST-Link, поэтому IDE читает с платы только то, что видно на экране.

**Как измерять.** Шаблон в отладке, открыты панели переменных, стека и один блок периферии; 20 шагов; время от нажатия до обновления всех панелей.

- [ ] 95-й перцентиль — не более 1 с.

#### P-07. Приём данных без потерь

Приоритет: Must · Проверка: Т

**Требование.** Монитор порта должен принимать непрерывный поток 115200 бит/с в течение 10 минут без потери данных.

**Обоснование.** 115200 — типовая скорость отладочного вывода. Если часть строк теряется, пользователь будет искать несуществующую ошибку в своей прошивке.

**Как измерять.** Тестовая прошивка непрерывно шлёт пронумерованные строки; IDE пишет лог (F-26); скрипт проверяет, что в нумерации нет пропусков.

- [ ] Ни одной пропущенной строки за 10 минут.  
- [ ] Интерфейс остаётся отзывчивым (P-02 выполняется).

### 3.5 Требования к логической базе данных

IDE не использует СУБД: все данные хранятся в текстовых файлах. Формат файлов выбирается на этапе 2\.

IDE хранит данные в трёх местах: в папке проекта (общие настройки проекта), в каталогах плат (описания железа) и в профиле пользователя Windows (личные настройки и кэши).

#### D-01. Файл проекта

Приоритет: Must · Источник: N-08 · Проверка: И

**Требование.** IDE должна хранить настройки проекта в текстовом файле в корне проекта, пригодном для хранения в Git.

**Пояснение.** В файле проекта — общие настройки, нужные обоим разработчикам: плата, конфигурации, макросы. Текстовый формат важен для Git: видно, что изменилось, и можно слить правки двух человек. Личное (точки останова, открытые вкладки, серийный номер своего ST-Link) хранится отдельно и в Git не попадает.

**Как должно работать:**

1. Имя и формат файла выбираются на этапе 2 (например, JSON или TOML).  
2. IDE записывает ключи в постоянном порядке и с отступами, чтобы одно изменение давало минимальную разницу в Git.  
3. В файле есть номер версии формата — для перехода на новые версии IDE.  
4. Личные данные лежат в отдельном файле, который шаблон проекта сразу добавляет в .gitignore.

**Критерии приёмки:**

- [ ] Изменение одной настройки меняет одну строку файла.  
- [ ] Файл читается и правится в обычном текстовом редакторе.  
- [ ] Личные настройки не попадают в общий файл.

#### D-02. Каталоги описаний плат

Приоритет: Must · Источник: N-09 · Проверка: Т

**Требование.** IDE должна читать описания плат из двух каталогов — встроенного и пользовательского; пользовательское описание с тем же идентификатором заменяет встроенное.

**Пояснение.** Встроенный каталог поставляется и обновляется вместе с IDE. Пользовательский принадлежит команде: там лежат описания собственных плат и исправленные копии встроенных. Обновление IDE никогда не трогает пользовательский каталог.

**Как должно работать:**

1. Встроенный каталог — в папке установки IDE (только чтение); пользовательский — в профиле пользователя; путь к нему можно изменить (например, на папку в общем Git-репозитории команды).  
2. Пути к SVD-файлу и шаблону внутри описания — относительные, от папки самого описания.  
3. При совпадении идентификаторов используется пользовательское описание, и в каталоге плат это помечается.

**Критерии приёмки:**

- [ ] Пользовательское описание с тем же идентификатором используется вместо встроенного.  
- [ ] Обновление IDE не изменяет пользовательский каталог.

#### D-03. Содержание описания платы

Приоритет: Must · Источник: N-09 · Проверка: И

**Требование.** Описание платы должно содержать: идентификатор, название, модель МК, объёмы Flash и RAM, интерфейс отладки, конфигурацию OpenOCD, путь к SVD-файлу и шаблон проекта.

**Пояснение.** Из этих полей IDE берёт всё, что нужно для создания проекта (F-01), отчёта о памяти (F-14), прошивки (F-16) и панели регистров (F-22). Ниже — пример для понимания; точный формат и имена полей утверждаются на этапе 2\.

```json
{
  "formatVersion": 1,
  "id": "nucleo-f401re",
  "name": "STM32 Nucleo-F401RE",
  "mcu": "STM32F401RE",
  "core": "cortex-m4",
  "memory": {
    "flash": { "origin": "0x08000000", "size": 524288 },
    "ram":   { "origin": "0x20000000", "size": 98304 }
  },
  "debug": {
    "probe": "stlink",
    "interface": "swd",
    "openocd": ["interface/stlink.cfg", "target/stm32f4x.cfg"],
    "connectUnderReset": false
  },
  "svd": "svd/STM32F401.svd",
  "template": "templates/stm32f4-blink"
}
```

**Критерии приёмки:**

- [ ] Формат описания платы документирован: каждое поле, его тип и обязательность.  
- [ ] Обязательные поля проверяются при загрузке (F-06).  
- [ ] Все встроенные описания проходят проверку.

#### D-04. Настройки IDE

Приоритет: Must · Источник: U-05 · Проверка: И

**Требование.** IDE должна хранить свои настройки (тема, клавиши, пути к инструментам) в профиле пользователя Windows.

**Пояснение.** У каждого пользователя Windows свои настройки, и для их записи не нужны права администратора.

**Как должно работать:**

1. Настройки — текстовый файл в папке приложения в профиле пользователя (например, `%APPDATA%\<IDE>`).  
2. Команда «Сбросить настройки» возвращает значения по умолчанию.  
3. Повреждённый файл настроек не мешает запуску: IDE сообщает об этом и использует значения по умолчанию.

**Критерии приёмки:**

- [ ] После удаления или повреждения файла настроек IDE запускается со значениями по умолчанию.  
- [ ] Настройки двух пользователей Windows не пересекаются.

#### D-05. Без сервера баз данных

Приоритет: Must · Источник: Р-07 · Проверка: И

**Требование.** IDE не должна требовать установки сервера баз данных.

**Пояснение.** Данных немного, и файлов достаточно; лишние службы усложнили бы установку и поддержку для команды из двух человек.

**Как должно работать:**

1. Все данные — файлы (D-01…D-04).  
2. Кэши (индекс clangd, разобранные SVD) лежат в отдельной папке кэша и могут быть удалены в любой момент.

**Критерии приёмки:**

- [ ] Установка IDE не требует сторонних служб.  
- [ ] После удаления папки кэша IDE работает, а кэш создаётся заново.

### 3.6 Ограничения проектирования

Ограничения проектирования не добавляют функций, а сужают свободу выбора на этапе архитектуры. Они вытекают из решений команды (1.6) и лицензий сторонних компонентов.

#### C-01. Язык реализации C++

Приоритет: Must · Источник: Р-04 · Проверка: И

**Требование.** IDE должна быть реализована на C++ (версия стандарта — на этапе 2).

**Пояснение.** C++ даёт скорость и низкое потребление памяти (P-01, P-05), но требует дисциплины: ошибки работы с памятью ведут к падениям (риск в 5.2).

**Что это значит на практике:** единый стандарт и компилятор для IDE; письменные правила кода (например, без «сырых» new/delete); статический анализ и санитайзеры в тестовых сборках.

- [ ] Весь код приложения написан на C++ (скрипты сборки и тестов — исключение).  
- [ ] Стандарт и правила кода описаны в руководстве разработчика.

#### C-02. Самостоятельное приложение

Приоритет: Must · Источник: Р-02 · Проверка: И

**Требование.** IDE должна быть самостоятельным приложением, не зависящим от платформ VS Code, Eclipse или Theia.

**Пояснение.** Так команда полностью контролирует продукт и не зависит от чужих обновлений. Обратная сторона: то, что такие платформы дают сразу (окна, вкладки, настройки), придётся делать самим или брать из библиотек.

**Что это значит на практике:** один установщик; для работы не нужны VS Code, Eclipse, Java или Node.js; библиотеки (интерфейс, редактор) встраиваются в само приложение.

- [ ] На чистом Windows IDE работает без установленных VS Code, Eclipse, Java и Node.js.

#### C-03. Windows 10 и 11

Приоритет: Must · Источник: Р-05 · Проверка: Т

**Требование.** MVP должен работать в Windows 10 и Windows 11 x64.

**Пояснение.** Обе версии широко используются; между ними бывают различия в драйверах и настройках безопасности. Windows на ARM в MVP не входит.

- [ ] HIL-тест (Q-09) и тест с пользователем (U-01) пройдены на Windows 10 и на Windows 11\.

#### C-04. Код ОС только в слое абстракции

Приоритет: Must · Источник: Р-05 · Проверка: И

**Требование.** Код, зависящий от ОС, должен находиться только в слое абстракции ОС (IF-SW-07).

**Пояснение.** Это основа будущего переноса на macOS и Linux (Q-10). Соблюдать правило с первого дня дёшево, а выносить разбросанный по проекту код Windows потом — дорого.

**Что это значит на практике:** отдельный модуль (например, `platform/windows`), весь остальной код компилируется без заголовков Windows.

- [ ] Правило проверяется автоматически в CI.

#### C-05. Кроссплатформенные библиотеки с совместимой лицензией

Приоритет: Must · Источник: Р-05, Р-06 · Проверка: А

**Требование.** Библиотеки интерфейса и редактора должны работать в Windows, macOS и Linux и иметь лицензию, совместимую с лицензией IDE.

**Пояснение.** Выбор библиотеки интерфейса — главное решение этапа 2: от него зависят скорость разработки, внешний вид и переносимость. Возможные кандидаты для анализа: Qt, wxWidgets, Dear ImGui для интерфейса; Scintilla или встроенный редактор выбранной библиотеки для кода. Их лицензии и возможности проверяются на этапе 2\.

**Что это значит на практике:** сравнение кандидатов по критериям: поддержка трёх ОС, лицензия, зрелость и активность развития, качество компонента редактора кода, размер дистрибутива, сложность освоения.

- [ ] На этапе 2 сравнение кандидатов выполнено и задокументировано.  
- [ ] Пробный прототип на выбранных библиотеках собирается в Windows, macOS и Linux.

#### C-06. GPL-инструменты — только отдельными процессами

Приоритет: Must · Источник: Р-06 · Проверка: И

**Требование.** Внешние GPL-инструменты (GCC, GDB, OpenOCD) должны запускаться только отдельными процессами, без компоновки с кодом IDE.

**Пояснение.** Лицензия GPL требует распространять под GPL код, который с ней компонуется. Запуск инструмента отдельной программой с обменом через командную строку или сокет оставляет команде свободу выбора лицензии для самой IDE. Окончательную оценку лицензионных вопросов лучше подтвердить у юриста.

**Что это значит на практике:** инструменты загружаются с официальных источников (F-05), а не встраиваются; в репозитории ведётся реестр всех зависимостей с их лицензиями.

- [ ] В коде IDE нет компоновки с библиотеками под GPL.  
- [ ] Реестр зависимостей с лицензиями актуален на момент релиза.

#### C-07. Стандартные CMake-проекты

Приоритет: Must · Источник: N-08 · Проверка: Т

**Требование.** Проекты пользователя должны быть стандартными CMake-проектами, которые собираются командой cmake без IDE.

**Пояснение.** Проект не «заперт» в IDE: его можно собрать на сервере CI, в другой среде или из командной строки.

**Что это значит на практике:** шаблон содержит всё для сборки, включая toolchain-файл, а в его README написана команда сборки.

- [ ] Проект из шаблона собирается в терминале командами cmake без запуска IDE.  
- [ ] Размеры секций .elf совпадают со сборкой из IDE.

### 3.7 Соответствие стандартам

#### C-08. Открытые протоколы и форматы

Приоритет: Must · Источник: IF-SW-04…IF-SW-06 · Проверка: И

**Требование.** Обмен с clangd должен соответствовать спецификации LSP \[6\], с GDB — интерфейсу GDB/MI \[5\], чтение SVD — формату CMSIS-SVD \[7\].

**Пояснение.** Работа по открытым спецификациям, а не под особенности одной программы, позволяет заменить компонент (например, OpenOCD на другой GDB-сервер) без переписывания IDE.

- [ ] Клиенты LSP, GDB/MI и чтение SVD реализованы по указанным спецификациям; особенности конкретных инструментов вынесены в отдельные места кода.

#### C-09. Ведение требований

Приоритет: Must · Источник: Р-07 · Проверка: И

**Требование.** Изменения требований должны вноситься в этот документ по правилам ISO/IEC/IEEE 29148 \[1\] и фиксироваться в истории изменений.

**Пояснение.** Требования будут меняться по ходу работы. Важно, чтобы SRS оставался единственным источником правды, а решения не терялись в переписке.

**Что это значит на практике:** любое изменение — правка SRS, запись в истории и новая версия; номера требований не переиспользуются; удалённое требование помечается «Удалено», а не стирается.

- [ ] У каждой версии SRS есть запись в истории изменений.  
- [ ] Номера требований уникальны и не переиспользуются.

### 3.8 Атрибуты программной системы

Атрибуты качества описывают, насколько IDE надёжна, безопасна и удобна в сопровождении. Для команды, которая ставит качество выше скорости (Р-07), эти требования так же важны, как функции.

#### Q-01. Надёжность: падение инструмента

Приоритет: Must · Проверка: Т

**Требование.** Аварийное завершение компилятора, OpenOCD, GDB или clangd не должно завершать IDE: IDE показывает сообщение и предлагает перезапустить инструмент.

**Пояснение.** Внешние инструменты — чужие программы, они могут упасть или зависнуть. Так как они работают отдельными процессами, их падение можно изолировать от самой IDE.

**Как должно работать:**

1. IDE отслеживает завершение каждого процесса и его код возврата; для долгоживущих — ещё и таймаут ответа.  
2. Упавший clangd перезапускается автоматически (несколько попыток), затем пользователь получает сообщение.  
3. При падении GDB или OpenOCD сеанс отладки завершается с сообщением и кнопкой «Перезапустить отладку».  
4. Зависший процесс принудительно завершается по таймауту.

**Критерии приёмки:**

- [ ] Принудительное завершение каждого инструмента через диспетчер задач не роняет IDE.  
- [ ] После падения clangd подсказки в редакторе восстанавливаются сами.

#### Q-02. Надёжность: восстановление несохранённых изменений

Приоритет: Should · Проверка: Т

**Требование.** IDE должна сохранять резервную копию несохранённых изменений не реже раза в 60 с и предлагать их восстановить после аварийного завершения.

**Пояснение.** Даже если сама IDE упадёт или выключится питание, работа последних минут не должна теряться.

**Как должно работать:** копии хранятся в профиле пользователя, а не рядом с исходниками; при нормальном закрытии удаляются; после сбоя IDE предлагает список файлов для восстановления.

**Критерии приёмки:**

- [ ] После принудительного завершения IDE изменения, сделанные 60 с назад и раньше, восстанавливаются.  
- [ ] Резервные копии не попадают в папку проекта.

#### Q-03. Надёжность: отключение платы

Приоритет: Must · Проверка: Т

**Требование.** При отключении платы во время прошивки или отладки IDE должна завершить сеанс с сообщением, не зависая.

**Пояснение.** Выдернутый кабель или перезагрузка платы по питанию — обычное дело при работе с железом, а не исключительная ситуация.

**Как должно работать:** отключение распознаётся по ошибке OpenOCD/GDB или событию USB; сеанс завершается, процессы закрываются, пользователь видит «Связь с платой потеряна»; после подключения отладку можно сразу запустить снова.

**Критерии приёмки:**

- [ ] Отключение USB во время шага, во время работы программы и во время прошивки не приводит к зависанию IDE.  
- [ ] После повторного подключения отладка запускается без перезапуска IDE.

#### Q-04. Доступность: работа без интернета

Приоритет: Must · Проверка: Т

**Требование.** После установки инструментов все функции IDE должны работать без доступа к интернету.

**Пояснение.** Работа с железом часто идёт в лаборатории, на объекте или с ноутбуком без сети.

**Критерии приёмки:**

- [ ] При отключённой сети работают создание проекта, сборка, прошивка, отладка и монитор порта.

#### Q-05. Безопасность: проверка загруженных файлов

Приоритет: Must · Проверка: Т

**Требование.** IDE должна проверять контрольную сумму SHA-256 каждого загруженного инструмента до установки.

**Пояснение.** Это защита от повреждения файла и от подмены. Контрольные суммы хранятся в манифесте внутри самой IDE, а не скачиваются рядом с файлом — иначе злоумышленник может подменить оба.

**Критерии приёмки:**

- [ ] Файл с изменённым байтом отвергается с сообщением и удаляется.

#### Q-06. Безопасность: никакой скрытой передачи данных

Приоритет: Must · Проверка: И

**Требование.** IDE не должна передавать телеметрию или данные проекта без явного согласия пользователя.

**Пояснение.** Исходники прошивок — интеллектуальная собственность. Если когда-нибудь понадобится анонимная статистика, она включается только пользователем и только с понятным описанием того, что передаётся.

**Критерии приёмки:**

- [ ] В коде нет сетевых обращений вне модуля загрузки (IF-COM-01).  
- [ ] Сетевой монитор во время обычной работы не фиксирует соединений, кроме локального TCP между GDB и OpenOCD.

#### Q-07. Безопасность: без прав администратора

Приоритет: Must · Проверка: Т

**Требование.** IDE должна работать без прав администратора; они нужны только для установки драйвера ST-Link.

**Пояснение.** Программа, которая работает с минимальными правами, безопаснее и работает на компьютерах, где пользователь не администратор.

**Как должно работать:** установка в профиль пользователя; драйвер ST-Link — отдельный шаг, на котором IDE объясняет, зачем нужны права администратора.

**Критерии приёмки:**

- [ ] IDE устанавливается и работает под обычной учётной записью Windows.  
- [ ] Запрос прав администратора появляется только при установке драйвера.

#### Q-08. Сопровождаемость: модульные тесты и CI

Приоритет: Must · Проверка: И

**Требование.** Ядро IDE (разбор вывода инструментов, модель проекта, клиенты GDB/MI и LSP) должно быть покрыто модульными тестами, которые запускаются в CI на каждое изменение.

**Пояснение.** Автотесты ловят регрессии сразу, а не через недели. Особенно важны тесты разборщиков: они проверяются на записанном реальном выводе инструментов без железа.

**Как должно работать:** CI (например, GitHub Actions на Windows) собирает IDE и запускает тесты на каждое изменение; изменение с упавшими тестами не попадает в основную ветку.

**Критерии приёмки:**

- [ ] У каждого модуля ядра есть модульные тесты.  
- [ ] CI запускается на каждое изменение и блокирует слияние при падении тестов.

#### Q-09. Сопровождаемость: тест на железе перед релизом

Приоритет: Must · Проверка: Т

**Требование.** Перед каждым релизом должен выполняться автотест полного цикла на реальной плате: сборка, прошивка, остановка на точке останова.

**Пояснение.** Прошивку и отладку нельзя полностью проверить без железа. Тестовый стенд — ПК с подключёнными Nucleo-F401RE и Nucleo-F103RB.

**Как должно работать:** скрипт создаёт проект из шаблона, собирает, прошивает, запускает отладку, доходит до точки останова, проверяет значение переменной и вывод в UART. Запускается перед релизом вручную или автоматически на стенде.

**Критерии приёмки:**

- [ ] Сценарий автоматизирован и проходит на обеих платах.  
- [ ] Результат прогона прилагается к релизу.

#### Q-10. Переносимость на macOS и Linux

Приоритет: Should · Проверка: А

**Требование.** Перенос на macOS или Linux не должен требовать изменений вне слоя абстракции ОС и сборочных скриптов.

**Пояснение.** Это следствие IF-SW-07, C-04 и C-05: если они соблюдены, перенос сводится к написанию новой реализации слоя ОС.

**Критерии приёмки:**

- [ ] Перечень мест, зависящих от ОС, совпадает с содержимым слоя абстракции (анализ).  
- [ ] Желательно: ядро IDE без интерфейса собирается в CI и под Linux.

#### Q-11. Расширяемость: новая плата без изменения кода

Приоритет: Must · Проверка: Т

**Требование.** Новая плата STM32 должна добавляться только файлом описания (D-02), без изменения кода IDE.

**Пояснение.** Собственные устройства команды могут стоять на разных чипах STM32; поддержка нового чипа не должна требовать новой версии IDE.

**Критерии приёмки:**

- [ ] Плата другой серии STM32, отсутствующая во встроенном каталоге, добавлена только файлом описания; проект для неё создаётся, прошивается и отлаживается.

#### Q-12. Открытость исходного кода

Приоритет: Must · Проверка: И

**Требование.** Исходный код IDE должен публиковаться в открытом репозитории под открытой лицензией (выбор лицензии — 5.3).

**Пояснение.** Решение команды (Р-06). Чтобы открытый проект был полезен другим, по нему должно быть понятно, как собрать IDE и как предложить изменение.

**Как должно работать:** публичный репозиторий; в корне — файл лицензии, README с инструкцией по сборке и CONTRIBUTING с правилами для участников.

**Критерии приёмки:**

- [ ] Репозиторий публичен, лицензия выбрана и указана.  
- [ ] IDE собирается из исходников по инструкции из README на чистой машине.

### 3.9 Вспомогательная информация

Анализ аналогов (STM32CubeIDE, PlatformIO, расширение STM32 для VS Code, Keil MDK) и обоснование выбора STM32 содержатся в исходном анализе требований. Риски реализации — в приложении 5.2.

## 4\. Верификация

Каждое из 82 требований раздела 3 имеет метод верификации; MVP принимается, когда выполнены все 63 требования Must (критерии — в 4.4).

### 4.1 Методы

| Код | Метод | Что делаем | Для каких требований |
| :---- | :---- | :---- | :---- |
| И | Инспекция | Просматриваем код, конфигурацию, документы и лицензии по чек-листу | Ограничения проектирования, форматы данных, структура кода |
| А | Анализ | Оцениваем расчётом или разбором зависимостей, без запуска | Переносимость, совместимость лицензий |
| Д | Демонстрация | Показываем функцию в работе и сравниваем с ожидаемым поведением, без измерений | Пользовательский интерфейс |
| Т | Тест | Выполняем сценарий с заданными входными данными и проверяем результат по измеримому критерию | Функции, интерфейсы, производительность, надёжность |

### 4.2 Уровни проверки

1. **Модульные тесты** — ядро IDE, автоматически в CI на каждое изменение (Q-08).  
2. **Интеграционные тесты** — с настоящими GCC, CMake, OpenOCD, GDB и clangd на Windows, без платы.  
3. **Тесты на железе (HIL)** — полный цикл на платах Nucleo перед каждым релизом (Q-09).  
4. **Измерения производительности** — на эталонном ПК из 3.4.  
5. **Тест с пользователем** — человек, не участвовавший в разработке, на чистом ПК (U-01).
